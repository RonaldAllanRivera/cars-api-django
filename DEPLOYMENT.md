# Deployment (free tiers)

The whole demo runs on free plans. No credit card is needed for any of them.

| Component | Host | Defined by |
|---|---|---|
| Django API + admin | Render, Docker web service | [`render.yaml`](render.yaml), [`backend/Dockerfile`](backend/Dockerfile), [`backend/bin/start.sh`](backend/bin/start.sh) |
| PostgreSQL | Neon | Manual, step 1 |
| Vue web client | Netlify | [`.github/workflows/web.yml`](.github/workflows/web.yml) |
| Expo web build | Netlify | [`.github/workflows/mobile.yml`](.github/workflows/mobile.yml) |

Order matters: create the database, then the API (the clients need its URL),
then the two Netlify sites, then go back and allow their origins through CORS.

---

## 1. Database: Neon

Why not Render's own PostgreSQL? A free Render database **expires 30 days after
creation** and is deleted after a short grace period. Neon's free tier does not
expire.

1. Sign up at <https://neon.tech> and create a project. Pick the region closest
   to the Render region in `render.yaml` (`oregon` = US West).
2. **Dashboard → Connect.** Leave **Connection pooling off** so you get the
   *direct* host (no `-pooler` in the name). Django holds persistent connections
   and uses server-side cursors, which a transaction-mode pooler breaks.
3. Copy these values for step 2:

   | Neon shows | Render variable |
   |---|---|
   | host, e.g. `ep-cool-name-123456.us-west-2.aws.neon.tech` | `DB_HOST` |
   | database, e.g. `neondb` | `DB_DATABASE` |
   | role, e.g. `neondb_owner` | `DB_USERNAME` |
   | password | `DB_PASSWORD` |

   `DB_PORT=5432` and `DB_SSLMODE=require` are already set by the Blueprint.

Neon suspends an idle database after a few minutes; the first query after that
takes a moment longer. Nothing to configure.

## 2. API: Render

1. Push this repository to GitHub.
2. Sign up at <https://render.com>, then **New → Blueprint** and pick the repo.
   Render reads `render.yaml` and proposes one free web service,
   `cars-images-api`.
3. Fill in the `sync: false` values it prompts for:

   | Variable | Value |
   |---|---|
   | `APP_URL` | `https://cars-images-api.onrender.com` (your service's URL; if the name is taken, Render appends a suffix; fix this value after the first deploy) |
   | `DB_HOST`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` | From step 1 |
   | `CORS_ALLOWED_ORIGINS` | Leave as `http://localhost:5173` for now; step 4 sets the real one |
   | `ADMIN_NAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Your admin login. Use a long password: weak ones are rejected and stop the boot |
   | `WIKIMEDIA_USER_AGENT` | `CarsImagesApi/1.0 (https://github.com/<you>/cars-api-django; you@example.com)` with a **real** contact. Wikimedia blocks generic agents |

   `APP_KEY` is generated by Render. Every other setting has a sensible default;
   see [`.env.example`](.env.example) for the full list.
4. **Apply.** The first build takes a few minutes. The free tier has no shell
   and no pre-deploy command, so the container does its own setup on every
   boot ([`bin/start.sh`](backend/bin/start.sh)): `migrate`,
   `createcachetable`, `ensure_admin`, `seed_catalog --if-empty`, then gunicorn.
   All of these are idempotent. Watch them in **Logs**.
5. Render deploys `main` automatically once its GitHub checks pass
   (`autoDeployTrigger: checksPass`).

> **Cold starts.** A free instance spins down after **15 minutes** without
> traffic and takes **about a minute** to wake; the first request waits for it.
> Before a demo or an interview, open `https://<service>.onrender.com/up` and
> wait for `{"status": "ok"}`.

Each boot re-applies `ADMIN_PASSWORD`, so change the password in Render's
**Environment** page, not in the admin UI.

## 3. Clients: two Netlify sites

Both clients are built in GitHub Actions and uploaded as finished `dist/`
folders. **Do not link the repository in Netlify** ("Import from Git"): Netlify
would rebuild both sites on every commit to this monorepo, with build settings
that live outside version control.

1. Sign up at <https://netlify.com>. Create **two empty sites** (Add new site →
   Deploy manually, and drop any placeholder folder), e.g. `cars-images-web`
   and `cars-images-mobile`. Rename them now if you want; the URLs go into CORS.
2. Note each site's **Site ID** (Site configuration → General).
3. Create a token: **User settings → Applications → Personal access tokens**.
4. In GitHub: **Settings → Secrets and variables → Actions**.

   | Name | Tab | Value |
   |---|---|---|
   | `NETLIFY_AUTH_TOKEN` | Secrets | The personal access token |
   | `NETLIFY_WEB_SITE_ID` | Secrets | Site ID of the Vue site |
   | `NETLIFY_SITE_ID` | Secrets | Site ID of the Expo site |
   | `VITE_API_URL` | **Variables** | `https://<service>.onrender.com` |
   | `EXPO_PUBLIC_API_URL` | **Variables** | `https://<service>.onrender.com` |
   | `WEB_DEPLOY_ENABLED` | Variables | `true` |
   | `MOBILE_DEPLOY_ENABLED` | Variables | `true` |

   The two API URLs go under **Variables**, not Secrets. They are compiled into
   public JavaScript anyway, and the workflows read `vars.*`: a value stored as
   a secret reads as empty, and the deploy job fails on purpose rather than
   publishing a site where every request breaks.
5. **Actions → Web CI → Run workflow** on `main`, then the same for **Mobile
   CI**. Later deploys happen on every push to `main` that touches `web/` or
   `mobile/`. Re-run manually after changing an API URL variable, because the
   URL is baked in at build time.

## 4. Allow the clients through CORS

On Render, **Environment**, set both Netlify origins (exact, no trailing slash)
and save. Render redeploys.

```
CORS_ALLOWED_ORIGINS=https://cars-images-web.netlify.app,https://cars-images-mobile.netlify.app
```

A CORS failure does not look like an auth failure: sign-in appears to do
nothing, and the browser console shows a blocked `OPTIONS` preflight. Check this
first if login silently fails.

## 5. Smoke checks

```bash
API=https://<service>.onrender.com

# Health (wakes a sleeping instance; allow about a minute)
curl -sS "$API/up"                              # {"status": "ok"}

# Admin login page renders and static files are served by WhiteNoise
curl -sS -o /dev/null -w '%{http_code}\n' "$API/admin/login/"   # 200

# API login returns a bearer token
curl -sS -X POST "$API/api/v1/auth/login" \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{"email":"<ADMIN_EMAIL>","password":"<ADMIN_PASSWORD>","device_name":"smoke"}'

# CORS preflight from the web client's origin
curl -sS -o /dev/null -D - -X OPTIONS "$API/api/v1/auth/login" \
  -H 'Origin: https://cars-images-web.netlify.app' \
  -H 'Access-Control-Request-Method: POST' | grep -i access-control-allow-origin
```

Then sign in to `/admin/`, open both Netlify sites, sign in, and run one search.

## 6. Blog publishing (optional)

Nothing is written or published until you trigger it, so this can wait.

1. **WordPress.** Sign in to the web app with a **staff** account (the `blog:*` abilities
   are granted to staff only; sign out and in again after an upgrade so the token picks them
   up), open **Pipeline → WordPress plugin → Download plugin**, then in WordPress go to
   **Plugins → Add New → Upload Plugin** and activate **Cars Images Publisher**. It registers
   the post fields the API writes, copies SEO fields to Yoast SEO or Rank Math, and prints the
   meta tags itself when neither is installed. (`used-cars-search` 1.6.13+ does the same job
   and the two can run together.) Create a WordPress user with the `unfiltered_html`
   capability (an Administrator or Editor on a single site), then
   **Users → Profile → Application Passwords** and create one.
2. **Render → Environment**, set:

   | Variable | Value |
   |---|---|
   | `ANTHROPIC_API_KEY` | From console.anthropic.com |
   | `ANTHROPIC_MODEL` | `claude-haiku-4-5` (the cheapest current model) |
   | `AI_MONTHLY_BUDGET_USD` | `1` for the first run |
   | `WORDPRESS_BASE_URL` | The site's canonical `https://` root, no `/wp-json`. Redirects are refused |
   | `WORDPRESS_USERNAME`, `WORDPRESS_APP_PASSWORD` | From step 1 |
   | `WORDPRESS_HOMEPAGE_URL`, `WORDPRESS_SITE_NAME` | Optional; the homepage link heads each article |

3. **First run.** In the admin, approve a few images, select them under **Car images →
   Queue blog posts**, then **Blog posts → Write and publish selected**. Open the draft in
   WordPress: check the gallery opens as an editable block, the image credits, and the SEO
   fields in Yoast or Rank Math. Then raise `AI_MONTHLY_BUDGET_USD`.

A `401` that looks like a wrong password is usually Apache dropping the `Authorization`
header: add `SetEnvIf Authorization "(.*)" HTTP_AUTHORIZATION=$1` (or `CGIPassAuth On`) to
the site's `.htaccess`.

## Notes and limits

- **Wikimedia thumbnails.** Wikimedia's thumbnail CDN rejects many datacenter
  IP ranges, Render's included. Server-side downloads therefore fetch the
  original and resize it locally with Pillow. Browsers load thumbnails from
  their own IPs, so the image grids are unaffected.
- **Long requests.** Searches, CSV chunks, ZIP exports and blog publishing chunks run inside the request
  (no worker on the free tier). Gunicorn allows 180 s per request, and the
  pipeline caps (`CARS_BULK_RUN_MAX_SECONDS`, `CARS_BULK_DOWNLOAD_MAX_IMAGES`)
  keep requests well under that.
- **Memory.** 512 MB. Two gunicorn workers with four threads idle at about
  130 MB. If ZIP exports of large originals hit the limit, set
  `WEB_CONCURRENCY=1` on Render.
- **Error log.** Nothing prunes on a schedule. Use **Error events → Prune old
  entries** in the admin.
- **Health check host.** Django only answers hosts in `ALLOWED_HOSTS`. The
  Render hostname is added automatically from `RENDER_EXTERNAL_HOSTNAME`; a
  custom domain must be added through `APP_URL` or `ALLOWED_HOSTS`.
